# AdminBot (Favgame Discord Bot) — память проекта

Этот файл — полный перенос памяти Claude по проекту, собранный 2026-08-01, чтобы продолжить работу на другом устройстве. Здесь собрано всё, что обсуждалось и решалось в предыдущих сессиях, включая отклонённые варианты и открытые баги — не сокращайте при последующем редактировании, только дополняйте.

## Цель проекта

Discord-бот на `D:\ProgrammingProjects\Discord Bots\AdminBot`, основная фича: спросить у каждого участника сервера его любимую игру и выдать соответствующую роль с минимальными правами. Со временем проект вырос в полноценного admin-бота: верификация новых участников, живой ростер ролей, косметическая система цветных ролей ("аура"), и интеграция с Яндекс Музыкой.

Пользователь — новичок в разработке Discord-ботов, попросил разбивать работу на стадии и проверять каждую перед переходом к следующей.

## Стек и архитектура

- **Node.js + discord.js**, CommonJS (не ESM), кроме одного моста ниже.
- Структура: `src/index.js` (главный файл, интенты, роутинг interactionCreate/guildMemberAdd/channelCreate), `src/deploy-commands.js` (регистрация слэш-команд), `src/commands/*.js` (по одному файлу на команду), `src/services/*.js` (бизнес-логика), `data/*.json` (персистентное состояние, в `.gitignore`, не приходит через git — переносится вручную).
- Бот назван **"Haru"**, приглашён с правом `Manage Roles` (268435456) + scope `bot applications.commands`. Позже руками в Server Settings → Roles нужно ещё добавить `Connect` + `Speak` для голосовых функций (см. Stage 8).
- **Права — принципиальная позиция пользователя**: роль бота должна иметь минимально необходимые права. Discord всё равно требует, чтобы роль бота была выше любой роли, которую он выдаёт — это ограничение не обойти.
- **Окружение (Windows)**: node/npm не подхватываются в уже открытых терминалах пользователя, хотя `C:\Program Files\nodejs` есть в системном PATH — сказывается только на старых сессиях. При запуске npm/node через инструменты добавлять `$env:Path += ";C:\Program Files\nodejs"` (PowerShell) или `export PATH="$PATH:/c/Program Files/nodejs"` (Bash).

## История решений (важно не переоткрывать)

- **Стек**: выбран JS/discord.js вместо Python/discord.py (пользователь подтвердил комфорт с JS/Node).

Решение (гибридное): использовать Presence Intent как подсказку текущей активности, но всегда показывать интерактивную форму для явного подтверждения выбора. **Позже (Stage 3) от этого отказались полностью** — см. ниже.

### Stage 4 — Game→role маппинг и логика выдачи ролей — mostly done (2026-07-26)

Отдельная админ-команда `/make-ranks game: levels:` даёт админу сгенерировать полную лестницу из N тематических рангов для игр, которые того заслуживают (например Battlefront, PUBG) — админ вручную назначает ранги участникам, бот не отслеживает прогресс/скилл автоматически.

Новые сервисы:

- `src/services/roleNameGenerator.js` — промпты и санитизация, `generateSingleRoleName` и `generateRankNames`.
- `src/services/gameRoles.js` — персистит маппинг game→role в `data/gameRoles.json`, создаёт роль с 0 прав при первом использовании, дальше переиспользует.
- `src/services/rankGames.js` — персистит лестницы рангов в `data/rankGames.json`.
- `steamGames.js` расширен методом `getAppId(name)` для поиска appid под запрос описания.

`/favgame` (`execute`) теперь деферит ответ, создаёт/переиспользует роль на уникальную игру через `gameRoles.getOrCreateRole`, назначает её вызвавшему. Новая админ-команда `src/commands/makeranks.js`, защищена `setDefaultMemberPermissions(PermissionFlagsBits.ManageRoles)`.

**LLM backend — история метаний**:

### Stage 4.5 — Живой ростер + welcome-флоу — done (2026-07-26)
- `guildMemberAdd` постит приветственный embed (с нативом к `/fav-game`) в админ-настроенный канал (`/set-welcome-channel channel:`, хранится per-guild в `data/guildConfig.json`).
- `src/services/roster.js` поддерживает ОДНО авто-редактируемое embed-сообщение (не спамит новыми) в админ-настроенном канале (`/set-roster-channel channel:`), список всех отслеживаемых игр с текущими держателями роли как живые упоминания участников, сгруппировано по игре, источник данных — `role.members` напрямую из кэша Discord (не отдельное самописное хранилище "кто что выбрал"), поэтому всегда отражает реальность, включая ручные изменения ролей админом. ### Stage 4.6 — Система "аура" (self-service цветные роли) — done (2026-07-27)
Отдельно от игровых ролей — участник выбирает чисто косметическую цветную роль ("аура") из выпадающего списка, независимо от любимой игры.

- `src/services/auras.js`: персистит список аур в `data/auras.json` (`{name, color, roleId}`, БЕЗ поля emoji — явно удалено пользователем дважды, **не добавлять emoji обратно к аурам, названию или пикеру ни в каком виде**). `ensureSeeded(guild)` создаёт дефолтную палитру из 9 цветов (Огненная, Ледяная, Королевская, Изумрудная, Золотая, Тёмная, Розовая, Электрическая, Кровавая) при первом вызове для гильдии; `addAura`/`removeAura` дают админам управлять списком дальше.
- `src/services/auraPicker.js`: публикует/редактирует ОДНО сообщение (embed + `StringSelectMenu` с одной опцией на ауру, value = roleId) в админ-настроенном канале (`/set-aura-channel channel:`). Тело embed перечисляет каждую ауру как голое упоминание роли (`<@&roleId>`) без буллета/эмодзи — Discord рендерит текст упоминания в реальном цвете роли, что и служит превью цвета. Выбор новой ауры через select menu убирает у участника любую другую ауру-роль, которая у него уже есть (одна аура одновременно), и добавляет выбранную.
- Админ-команды: `/set-aura-channel`, `/add-aura name: color:` (без параметра emoji), `/remove-aura name:` (autocomplete из текущего списка).
- Роутинг взаимодействий: `interactionCreate` в `index.js` проверяет `interaction.isStringSelectMenu() && interaction.customId === auraPicker.SELECT_CUSTOM_ID` до веток autocomplete/chat-input.

### Stage 6.1 — Верификация/rules-гейт — IN PROGRESS, на середине дебага (2026-07-27) — **продолжить здесь в следующей сессии**

Дизайн: новым участникам авто-выдаётся роль "Не верифицирован" (0 прав), которой запрещён `ViewChannel` на всех обычных каналах, кроме двух админ-назначенных: "gate"-канал (получает персонализированный embed "Добро пожаловать в {guild}! {упоминание участника}... прочти правила {упоминание канала правил} и нажми Принимаю" на каждый join, аватар участника как thumbnail) и "rules"-канал (один статичный embed + кнопка "Принимаю", текст задаётся через модальное окно). Клик по "Принимаю" убирает роль Unverified и шлёт существующий nudge `/fav-game` в канал, на который указывает `/set-welcome-channel` (назначение этой команды было переосмыслено с "нудж при входе" на "нудж после верификации").

Новые файлы: `src/services/verification.js` (настройка роли/каналов, restrict/allow по каналам, `handleAccept`, `applyGateToNewChannel` для авто-гейта новых каналов, `assignUnverified`), `src/commands/setupverification.js` (`/setup-verification gate-channel: rules-channel:` — открывает модальное окно для текста правил, а не принимает его как обычную строковую опцию, т.к. правила длинные/многострочные). `guildConfig.js` расширен ID gate/rules каналов+сообщений, текстом правил, ID роли Unverified.

Проводка в `index.js`: `guildMemberAdd` теперь вызывает `verification.assignUnverified`, затем постит gate-embed (заменив старый прямой nudge `/fav-game` там); новый слушатель `channelCreate` авто-ограничивает любой новый канал через `applyGateToNewChannel`; `interactionCreate` роутит `isButton() && customId === verification.ACCEPT_CUSTOM_ID` и `isModalSubmit() && customId.startsWith('verify-setup:')` (customId модалки кодирует `gateChannelId`/`rulesChannelId`, т.к. модалки Discord иначе не могут нести состояние от вызвавшей команды).

**Баг #1 (исправлен в коде, ЕЩЁ НЕ переприменён на живом сервере)**: первая версия `verification.setup()` перебирала ВСЕ каналы гильдии через `guild.channels.fetch()`, включая категории (CATEGORY), и только *пропускала* gate/rules каналы, а не явно разрешала их. Так как каналы Discord без явного оверрайта роли наследуют оверрайт родительской категории, запрет на категорию каскадом скрывал и gate/rules каналы тоже (совпадает с отчётом пользователя: друг, который зашёл, не видел ни одного канала). Исправление: `setup()` теперь полностью пропускает `ChannelType.GuildCategory`, и вместо пропуска gate/rules каналов вызывает новый `allowChannel()` (явный оверрайт `ViewChannel: true` для Unverified) на них — это перебивает любой унаследованный запрет на уровне категории. **Это исправление ЕЩЁ НЕ переприменено на реальном сервере** — пользователю нужно заново запустить `/setup-verification` с теми же значениями `gate-channel`/`rules-channel` (можно переиспользовать тот же текст правил), чтобы протолкнуть исправленные оверрайты; до этого дебаг-дамп показывал, что у всех каналов, включая welcome/rules, всё ещё `deny=ViewChannel` для роли Unverified.

**Уточнение (2026-07-27): "Lara✨" — НЕ тестовый аккаунт этого проекта** — это тестовый аккаунт для совсем другого бота, к AdminBot отношения не имеет. Настоящий тестовый аккаунт для этого проекта — **RastusKrest**.

**Баг #2, всё ещё открыт (2026-07-27)**: после повторного запуска `/setup-verification` с новыми gate/rules каналами, RastusKrest зашёл и сайдбар корректно показал только 2 разрешённых канала (welcome, rules) — подтверждая, что исправление Бага #1 действительно работает на живом сервере. Но чат-вьюпорт автоматически открылся на содержимом канала **аура** вместо welcome. Проверены и исключены две возможные причины на стороне бота: (1) System Channel гильдии (Server Settings → Overview) подтверждённо установлен на "welcome", не на aura; (2) грепнули `index.js`/`verification.js` — ни один не ссылается на канал ауры нигде во флоу join/gate, только `gateChannelId`/`rulesChannelId`. Так как права сайдбара доказанно верны, текущая ведущая гипотеза — **клиентское восстановление "последнего просмотренного канала для этой гильдии" на стороне Discord**, связанное с тем, что RastusKrest — переиспользуемый тестовый аккаунт, у которого в более ранней тестовой сессии уже была открыта аура. Не баг логики бота. **Следующий шаг**: попросить RastusKrest полностью перезапустить клиент Discord (или использовать свежую браузерную/веб-сессию) и зайти/переоткрыть сервер заново; если вьюпорт корректно откроется на welcome — подтверждает теорию клиентского кэша, изменения кода не нужны. Если всё ещё глючит на доказанно свежем клиенте — считать новой зацепкой и расследовать дальше (это исключит теорию клиентского кэша).

Также добавлено: защита от двойного клика/гонки в `verification.handleAccept` (in-memory `Set`, ключ `guildId:memberId`), чтобы быстрые повторные клики по "Принимаю" не отправляли nudge после верификации дважды — обычные (не одновременные) повторные клики уже были безопасны, так как код проверяет, всё ли ещё есть у участника роль Unverified.

**DHB-3 реализация — важные находки, не переоткрывать без новой причины**:
- **`yt-dlp-exec` (изначально запланированный) отклонён** — его install-скрипт жёстко требует Python на хосте (`npx bin-version-check-cli python ">=2"`), падает если Python не установлен (как на этой машине). Это не бандлит-свой-бинарник паттерн, а host-зависимость — именно то, чего проект избегает. **Не возвращаться к `yt-dlp-exec`.**
- **Взамен — `yt-dlp-wrap-plus`** (не `yt-dlp-wrap`! оригинальный `yt-dlp-wrap` помечен в npm как "Package no longer supported", `yt-dlp-wrap-plus` — активно поддерживаемый форк, последний релиз 2025-11-14 на момент проверки). Даёт `YTDlpWrap.downloadFromGithub(path)` — качает нужный под платформу бинарник **явно, при первом использовании**, а не через install-скрипт с проверками хоста.

Это удобно совпадает с задачей многостаночности проекта — не нужно вручную переносить бинарник между устройствами, как `data/`.
- **Пакет — CommonJS, не ESM** (в отличие от `yamd2` в Stage 8) — но экспортирует класс через `exports.default`, поэтому `require('yt-dlp-wrap-plus')` даёт `{ default: YTDlpWrap }`, а не сам класс напрямую. В `src/services/youtubeMusic.js` используется `require('yt-dlp-wrap-plus').default`. **Не пытаться заменить на `await import(...)` — не нужно и не так работает с этим пакетом.**

Причина: анонимный (без cookie-авторизации) YouTube Mix без сигнала о вкусе слушателя чаще подстраховывается треками того же артиста/канала, а старая логика продолжения всегда затравливала следующий Mix ПОСЛЕДНИМ треком партии — если партия была однородной, однородность накапливалась по цепочке. Это не баг в смысле "сломано", а осознанная компенсация ограничения анонимного YouTube Mix — если пользователь опять пожалуется на однородность, крутить `RESEED_FROM_ORIGINAL_CHANCE` или расширять `RADIO_BATCH_SIZE`, а не считать это новым багом.

**Архитектура (важно для дальнейших правок)**:
- `src/services/musicPlayer.js` — остаётся чистым движком (очередь/voice/ffmpeg), НЕ импортирует `musicPanel.js` напрямую. Вместо этого — инжектированный колбэк `setOnUpdate(callback)`, вызываемый как `notify(state.guild)` из каждой мутирующей функции (playNext/pause/resume/stop/shuffleQueue/setVolume/toggleLoop/toggleAutoplay/back). **Причина, не архитектурная прихоть**: все сервисы в проекте экспортируют `module.exports = {...}` одним объектом в конце файла (полная переприсвойка, не мутация `exports`) — прямой циклический `require` между `musicPlayer.js` и `musicPanel.js` тихо сломался бы. Если понадобится ещё один модуль, которому нужно и дёргать musicPlayer, и получать от него уведомления — использовать тот же паттерн колбэка, не добавлять встречный `require`.
- `src/services/musicPanel.js` — рендер embed/кнопок и обработчик кликов, по образцу `roster.js`/`auraPicker.js` (сообщение редактируется на месте), но БЕЗ привязки к `guildConfig` — см. выше. Два входа: `refresh(guild)` (обновить на месте, no-op если панели ещё нет — используется колбэком `notify` и уведомлениями об изменении состояния) и `ensurePanel(channel, guild)` (обновить/переехать/создать — вызывается явно из `music.js` сразу после успешного `enqueue`/`playRadio`, т.к. только там известен канал, где реально стартовали трек).
- `musicPlayer.js` состояние на гильдию расширено: `guild` (кэш из `connect()`, нужен для notify без живого interaction), `resource` (для громкости), `volume` (0..2), `loopMode` (`off/track/queue`, 3-позиционный тоггл), `autoplayEnabled`, `history` (лимит 20, для Back), `panelChannelId`/`panelMessageId`, разовые флаги `nextFromHistory`/`forceAdvance` — они передаются через `AudioPlayerStatus.Idle`-хендлер в `playNext()`, чтобы отличать "трек кончился сам" (учитывает `loopMode==='track'`) от "нажали Skip" (`forceAdvance`, всегда идёт дальше) и от "нажали Back" (`fromHistory`, не пишет в историю повторно). **Если правишь `playNext`/`back`/`skip` — сохрани эту разницу, без неё Back и Loop=Track ломают друг друга.**
- `getQueue(guildId)` заменён на единый `getPanelState(guildId)` — используется и панелью, и `/music radio` (для seed из текущего трека).
- `requestedBy` (id пользователя) проставляется на трек в момент `enqueue`/`playRadio` (в `music.js`, из `interaction.user.id`), НЕ в `youtubeMusic.js` — тот остаётся Discord-агностичным.
- Позиция воспроизведения (`1:24/3:42` из референса) **сознательно не реализована** — в исходном ТЗ помечена как опциональная, а честный тикающий таймер означал бы редактировать сообщение раз в секунду → упереться в рейт-лимиты Discord.

**Проверено на данный момент**: `node --check` + require-smoke-тест по всем файлам (все экспорты на месте, циклический require не сломался, `setmusicchannel.js` подтверждённо удалён), `npm run deploy-commands` прошёл дважды (сейчас 10 команд: `/music` — 3 сабкоманды, `/set-music-channel` окончательно убрана), бот стартует без ошибок.

### Инцидент 2026-08-01: бот падал целиком от одной протухшей интеракции — не баг музыки, системная дыра

При первом живом тесте `/set-music-channel` (тогда ещё существовавшая) уронила весь процесс. Причина не в музыкальном коде: `interaction.deferReply()` упал с `DiscordAPIError[10062] Unknown interaction`, общий catch в `index.js`'s `interactionCreate` попытался отправить пользователю сообщение об ошибке через `interaction.reply(...)` — токен уже невалиден, второй вызов тоже кинул исключение, на этот раз необработанное → unhandled `'error'` event на `Client` → Node крашится, т.к. `client.on('error', ...)` в проекте не было нигде вообще. **Исправлено надёжно, не зависит от причины**: (1) fallback-reply в `index.js` обёрнут в свой `try/catch`; (2) добавлен `client.on('error', (error) => console.error(...))`. Если бот падает с необработанным `'error'` event на `Client` — первым делом проверять, что этот обработчик на месте.

**Но сама протухшая интеракция — не разовая случайность.** После фикса бот перестал падать, но `/music play` продолжал стабильно (не через раз) отвечать `Unknown interaction` на `deferReply`. Проверено напрямую: `curl` до `https://discord.com/api/v10/gateway` с этой машины в этот момент занимал **2.7–12 секунд** на голый GET-запрос (несколько попыток подряд) — Discord даёт всего 3 секунды на первый ответ на интеракцию. **Вывод: причина сетевая (медленное/нестабильное соединение до Discord с этой машины/сети прямо сейчас), не в коде бота.** При повторной проверке чуть позже та же команда `curl` отвечала за 0.6–1с — **сеть именно скачет (то быстро, то медленно), не стабильно плохая и не постоянно заблокирована**. Дальше оптимизировать код бесполезно — тут нужна диагностика сети/VPN на стороне пользователя. Похоже по духу на прошлый регион-блок Gemini (см. Stage 4, "История решений") — не факт что та же причина, но паттерн "что-то в сети до внешних сервисов у этого пользователя иногда барахлит" уже встречался. **Если снова пожалуются на "бот не отвечает"/"местами странно себя ведёт" — сначала гонять `curl -w "%{time_total}"` до `discord.com` несколько раз подряд, а не сразу лезть в код.** Именно эта нестабильность объяснила и жалобу "панель зависает, не обновляется" — панель обновляется только при УСПЕШНОМ прохождении `enqueue`/`ensurePanel`, а если `/music play` падает на `deferReply` из-за сети, до `ensurePanel` дело просто не доходит, старое сообщение-панель остаётся как есть.

**UX-правки после первого визуального ревью пользователя (2026-08-01, скриншот бота "Lara" как референс)**:
- Кнопкам панели добавлены текстовые подписи (`.setLabel(...)`) в дополнение к эмодзи — были только эмодзи без подписей. Подписи на русском (не как у Lara на английском) — для консистентности с остальным ботом, это осознанный выбор, не недосмотр.
- `musicPanel.handleButtonClick` больше не шлёт отдельное ephemeral-сообщение на каждый клик ("Громкость: 70%", "AutoPlay: включён" и т.п.) — пользователь явно попросил не захламлять чат. Теперь клик подтверждается тихо через `interaction.deferUpdate()`, а результат виден в самой панели (она и так обновляется через `notify`→`refresh` сразу после мутации состояния). Единственное исключение — отказ "зайди в тот же голосовой канал" остался видимым ephemeral-ответом (это не clutter, а нужное объяснение), и `playlist` остался ephemeral-ответом с embed'ом очереди (это не подтверждение действия, а запрошенная информация).

**Живой тест кнопок в Discord всё ещё системно не проводился до конца** — сеть мешала пройти дальше первого клика. Продолжить, когда соединение стабильно: `/music play`, проверить появление панели, все 10 кнопок (включая визуально — подписи и что чат не захламляется), и что повторный `/music play` в другом канале переносит панель туда.
